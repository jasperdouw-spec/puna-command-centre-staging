# Phase D1 schema and obligation-preserving containment

`db/proposals/phase_d1_ordering.sql` is an **unnumbered candidate**, not an approved hosted migration. Hostinger MCP now authenticates, but its available operations do not expose the installed SQL ledger. Existing migrations 001–008, startup and normal migration tooling are untouched. Do not assume 009 is free.

The candidate reuses `pickup_orders`, `pickup_order_lines`, `provider_events`, audit/rate-limit infrastructure and all six Phase C kitchen tables. It makes the old service-batch link nullable, adds a kitchen line stage, permits customer-created kitchen allocations without a staff creator, and adds a unique order link. Seven extension tables provide order access/packing metadata, payment attempts, hashed pickup tokens, idempotent order events, notification jobs, fake payment state and encrypted local email captures. The final two are explicitly D1 test-provider infrastructure, requiring separation from any future operational migration.

There is one payment/fulfilment owner (`pickup_orders`) and one physical commitment owner (its linked Phase C allocation). A payment/release/handover transaction changes both. Main legacy order lines retain their stage and service batch; existing balances, movements, historical sales and reporting are fingerprinted unchanged. Phase C fixture payment/collection and expiry skip/refuse customer-linked orders; legacy payment/refund/collection helpers refuse them. Frozen and scheduled legacy orders retain their existing workflow.

Only `tests/run-local-disposable.mjs` may create the test environment. It refuses local environment files, strips inherited DB/provider configuration, creates its own labelled tmpfs MariaDB 11.8.9 container on loopback, verifies ownership, applies candidates through guarded scripts, runs tests/recovery and removes only that container. Candidate application checks the exact Phase C checksum, collisions and rerun ledger consistency. Nothing is applied to a pre-existing database.

Before a future hosted proposal: read the actual engine/collation, definitions, migration ledger and constraints; select an unused number; verify a current private backup and restore; rehearse the exact additive change against a separately approved copy; review indexes, production provider separation, secrets/key rotation, retention and growth. DDL is not a transactional rollback strategy. No startup/build schema application is allowed.

## Containment

For the local D1 service, `PUNA_ORDERING_ACCEPT_NEW=false` is the intake stop. Leave `PUNA_ORDERING_LOCAL_ENABLED`, its disposable-local guards, Phase C kitchen service and encryption key intact while obligations exist. Existing payment reconciliation, customer status, notification captures, queue, packing and QR/manual handover remain available. Paused/Closed stops new allocation but permits safe fulfilment after a current physical review; stale heartbeat/review blocks physical mutations until reconnect/review. Reconciliation remains possible while stale.

Disabling the entire D1 service is appropriate only for an empty/drained demonstration or a deliberate outage with a separate obligation-resolution plan. The feature-off regression proves retained schema and legacy behavior, not permission to hide live paid orders. Do not route D1 obligations into legacy fulfilment, drop additive tables, automatically resell paid food, rotate away active token encryption keys, or automatically refund. A paid late-capture exception retains the original promise and requires owner/manager resolution if the exact basket cannot be restored.

The outbox and payment jobs are durable and lease-based. D1 tests pump them through a secret, loopback-only fixture endpoint; customer and worker actions also dispatch eligible local captures. No hosted scheduler has been installed. D2 must provide an approved, monitored reconciliation/delivery runner and real provider idempotency before any provider activation. A process restart preserves DB jobs and requires the same local encryption key; deleting the disposable database intentionally ends the demonstration.
