## 1. Square Sandbox payments

Authorize a dedicated PUNA development application and **Canadian Sandbox test seller/location**, separate from the production reporting OAuth application/connection. Approve creation only if the owner does not already have the intended application. Needed private configuration: Sandbox access token, application ID, merchant ID, CAD location ID, webhook signature key and exact notification URL; public client receives only Sandbox application/location IDs. Pin and record an API version before testing (official reference inspected at version 2026-09-16).

Prefer a scoped Sandbox OAuth token generated in the Developer Console. Minimal requested permissions for this plan: `PAYMENTS_WRITE`, `PAYMENTS_READ`, `MERCHANT_PROFILE_READ` for merchant/location verification. `CreatePayment` and `RefundPayment` need `PAYMENTS_WRITE`; extra-recipient permission is relevant only to application fees, which this plan does not use. No customer, catalogue, inventory, bank-account or production write permission is requested. The local order ID travels as `reference_id`; no Square Orders integration is planned here. Adding it would require a separate reviewed `ORDERS_READ`/`ORDERS_WRITE` scope decision. [Square Sandbox](https://developer.squareup.com/docs/devtools/sandbox/overview), [permissions](https://developer.squareup.com/docs/oauth-api/square-permissions), [CreatePayment](https://developer.squareup.com/reference/square/payments-api/create-payment), [RefundPayment](https://developer.squareup.com/reference/square/refunds-api/refund-payment).

Proposed endpoints: `https://<approved-ephemeral-host>/api/ordering/square/webhook` for `payment.created`, `payment.updated`, `refund.created`, `refund.updated`; customer return `https://<approved-ephemeral-host>/order-status#<opaque-token>`. The webhook path is proposed, not implemented/registered by D1. No OAuth redirect is needed for a Console-generated Sandbox token; a future browser OAuth flow would separately register `/api/ordering/square/oauth/callback` on that same approved origin. Never reuse the reporting callback or production reporting token.

A secure temporary HTTPS tunnel is needed to receive provider callbacks on a local server and to test another physical device, unless an explicitly approved isolated test host is supplied. Approval must name the provider, exact ephemeral origin, permitted routes, access controls, time limit and cost cap. Expose only the intended test app/webhook; the D1 fixture route must stay unreachable externally. D1 loopback gates must not simply be disabled: implement a separately reviewed Sandbox adapter/environment guard, recipient/test data restrictions, CSP and provider-specific identity normalization. Prefer developer Console subscription setup rather than granting webhook-management API scopes.

Square sends an HMAC signature over the exact registered URL and raw body using the subscription key. D2 must verify `x-square-hmacsha256-signature` with constant-time comparison, then independently retrieve and verify payment amount/currency/order reference/location/seller. D1's fake signature format is intentionally not a Square-compatible webhook. [Signature requirements](https://developer.squareup.com/docs/webhooks/step3validate).

Approve only provider test cards/tokens and synthetic orders: success, decline, pending/capture/cancel, duplicate create with one stable key, disconnect/timeout, duplicate/out-of-order/forged webhooks, restart/reconciliation, mismatched identity/amount, and last-unit/late-capture isolation. Use a capped batch, for example no more than 30 synthetic CAD payments at configured basket totals and 10 Sandbox full/partial refund attempts. Refund idempotency, authoritative completion and stock disposition need separate implementation/review before exercising that API; no automatic real refund is authorized. Sandbox does not accept real cards or support card-present testing. [Sandbox payments](https://developer.squareup.com/docs/devtools/sandbox/payments).

Evidence: sanitized request identities, state transitions, webhook signature decisions, provider retrieval checks, event deduplication, reconciliation leases, stock invariants, refund results and screenshots without card/customer/token/secret data. Avoid card data in logs. Cleanup: close intake, reconcile all attempts/refunds, drain orders/jobs, remove the test subscription/tunnel, revoke disposable credentials and remove only the owned synthetic database. Retain redacted evidence. Production reporting OAuth scopes/jobs and hosted checkout remain unchanged.
