# Phase C provisional schema and rollback

Candidate: `db/proposals/phase_c_live_kitchen.sql`. It deliberately has no numeric migration assignment. Current hosted schema/migration history is unavailable, so compatibility and a release migration number remain **provisional**. Existing migration files 001–008 and the normal migration runner are unchanged. No startup/build applies SQL.

The candidate adds six InnoDB tables: singleton kitchen mode/version/heartbeat/review/hold policy; actor/client observations; physical product lots; reservations; reservation-to-lot lines; and an idempotent event journal. Existing products/users are referenced with foreign keys. Counters are unsigned; allocation lines constrain ready/set-aside quantities. Shortage is allowed between physical stock and commitments so wastage can be truthfully recorded without deleting obligations. The default state is Closed with no stock, lease, review or reservations; unpaid hold policy is 300 seconds.

`tests/apply-kitchen-schema.mjs` is an application mechanism **only for the new disposable test database**. It invokes the existing Docker ownership/image/mount/port guard, accepts the fixed synthetic database/user/password, verifies prior 006/008 checksums and InnoDB prerequisites, and records `phase_c_live_kitchen_candidate_v1` in the synthetic migration ledger. It refuses checksum drift, colliding partial tables or a ledger with missing tables. No existing local, staging or production database is authorized.

The application serializes mutations using the existing transaction lock and kitchen-state row lock, uses database time and optimistic stock versions, and commits the event/audit with the physical change. All requested basket lines are validated before creation. SQL errors roll the transaction back. Counter consumption retires physical and committed units together. A repeated operation key returns the original result only for the same actor and request hash.

Flags are independent and default false: `PUNA_LIVE_KITCHEN_ENABLED`, `PUNA_KITCHEN_PUBLIC_PREVIEW`, `PUNA_KITCHEN_FIXTURES`. Feature-off owner/worker screens use their original paths; kitchen endpoints refuse operations and the availability endpoint returns disabled without accessing kitchen tables. Fixture actions require additional disposable-local and loopback synthetic database guards. Never enable fixture flags on hosting.

Before a future migration: regain read-only hosting access; inspect exact table engines, character sets/collations, key definitions, installed migration ledger and existing order/stock commitments; select an unused migration ID; verify a current private backup and isolated restoration; rehearse on an approved isolated copy; and obtain exact migration/release approval. Resolve operational stocktake provenance and legacy/frozen boundaries before populating lots. Do not import historical sales into physical stock.

Rollback: first pause new online reservations and inspect/drain or explicitly reconcile protected holds, uncertain payments, paid items and counter reservations. Turning flags off hides the new experience and blocks new kitchen actions; it retains all tables and commitments. Existing legacy tools continue to work. Feature-off is a containment switch, not a way to fulfil or erase kitchen obligations. Do not drop tables, reset quantities or migrate new orders into the old fulfilment path. Restore from backup only under a separate approved recovery plan; any replay must reconcile event identities and provider state first.

The disposable suite verifies candidate rerun/missing-table refusal, feature-off operation before and after the schema, preservation of legacy stock/order/reporting fingerprints, and synthetic recovery. Those checks do not establish hosted compatibility, real-data restore readiness or approval to deploy.
